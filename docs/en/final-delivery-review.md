The behavior is reflected in the Standard Table, Standard Table Tabs and EditableTable demos.

The development-memory review found a concrete source of process accumulation. When `--apps` spawned child applications, the CLI's SIGINT/SIGTERM handlers stopped those children but consumed the parent dev server's default exit signal. The CLI now stops child apps and re-delivers the original signal to the parent, with a regression test. After restart, port 9001 has one listener. Two short samples showed RSS fall from about 88MB to 77MB with CPU around 0.7%, so no sustained growth was observed. The standard Table page has 2,298 DOM nodes, 21 rows and 441 cells; the browser did not expose its JS heap metric, so this does not establish a long-term memory curve. The `--apps` shutdown bug could leave services behind across repeated starts; the current single-Portal service has no duplicate instance, and this evidence does not attribute every OOM to that one cause.

## 2026-10-23 Runtime default-locale request-loop regression

The development-memory review found a second concrete loop. When `localeUrl` is configured and `locales` is omitted, Runtime copied the default locale list on every render. Loading the locale resource updates revision state, which changed the locale-options reference and restarted the fetch effect for the same locale. In one earlier observation window of about 19 seconds, `demo-locale.json?locale=zh-CN` was requested about 250 times; the browser task manager showed roughly 133% CPU and 13.1GB for that page, with about 593 DOM nodes and a 131MB JS heap. This evidence matches a sustained request loop but does not establish that every development OOM has the same cause.

Runtime now keeps the default locale list, supported locale codes and valid locale options referentially stable, so the resource effect does not restart after its own successful state update. A JSDOM integration regression mounts the real `BiuShell` with default locales and asserts one locale request across resource loading and the resulting rerender; it passes. Some older In-app Browser tabs still show Chromium crash pages, but a healthy tab later reopened `StandardTablePageShowcase`; its filter area, toolbar, full table and pagination rendered normally, and the three standard Table pages plus resize cases passed browser regression. The restarted 9001, 8001 and 8002 services all return HTTP 200, with one listener per port. At 21m56s and 22m13s after startup, RSS stayed near 77/64/64MiB, CPU was 0%, system available memory was about 52%, and no memory throttling was observed. This short observation measures server processes, not browser renderers or long-term memory growth; the cause of the old renderer crashes remains unconfirmed.

Changesets versioned the affected packages as stable releases: `@biugle/biu-cli` 1.0.2, `@biugle/biu-store` 1.0.1, `@biugle/biu-runtime` 1.0.3 and its dependent `@biugle/biu-preset` 1.0.3. The locale request-loop fix is in Runtime 1.0.2; Runtime was then bumped to 1.0.3 for the Store dependency update, and Preset was aligned to 1.0.3. The source Changeset was consumed by `changeset version`; package, changelog and lockfile changes remain uncommitted. The repository has no prerelease configuration or prerelease suffix on current package versions. npm was not published in this run. A read-only npm registry check confirmed that none of the 18 stable candidates appeared in the published version lists; existing stable versions currently top out at 0.6.0 or 0.4.0. npm may retain early temporary prerelease versions in package history; published history cannot be rewritten, and this release only publishes stable candidates that have not been published before.

### High-priority findings

#### F-01 React peer dependency contracts are inconsistent (P1)

@biugle/react-components, @biugle/react-table and @biugle/biu-runtime declare React/ReactDOM >=18 in peerDependencies while also placing React ^19.0.0 in dependencies. react-components also directly depends on ReactDOM 19. @biugle/biu-preset and @biugle/biu-adapter-react depend on React/ReactDOM 19 without declaring React peers. Workspace Demos use React 19, so current type checks and builds do not expose the React 18 external-consumer risk.

A React 18 host may resolve both host React 18 and package-local React 19, leading to duplicate React instances, mismatched Hook dispatchers or root-mount behavior. The current pack check validates archive contents and export targets, not external installation. Before the next public release, standardize the host dependency policy: make React/ReactDOM peers, keep development versions in devDependencies and publish only a range that has been tested. Add packed-consumer fixtures for React 18 and 19, assert a single React instance and render Runtime, Preset, UI components and Adapter.

#### F-02 The iframe sandbox allows scripts and same-origin content, while same-origin APP URLs are accepted (P1, conditional security risk)

packages/runtime/src/remote.tsx always sets sandbox="allow-scripts allow-same-origin allow-forms allow-popups allow-modals". The CLI does not require ALLOWED_ORIGINS for relative APP_URLs, Runtime resolves relative URLs against the Portal origin, and the current unit test explicitly accepts /same-origin. When remote content resolves to the Portal's own origin, combining allow-scripts with allow-same-origin weakens sandbox isolation: same-origin script can access the embedded element and attempt to remove the restriction. Repository policy calls for separately hosted Portal/APP domains, but the implementation does not enforce that condition.

This was not reproduced with the current separate-origin Demo topology; it is a defense-in-depth gap that allows a risky configuration. Explicitly reject same-origin production APPs or remove allow-same-origin for that case and validate the required Cookie/Bridge behavior. Add integration cases for same-origin, cross-origin, relative URLs and malicious Origins.

#### F-03 UI regression is not part of CI, and complex Preset has no package test suite (P1)

pnpm verify covers types, Node/JSDOM unit tests, CLI scenarios and Demo builds, but has no Playwright/Cypress browser task, visual snapshots, axe/WCAG scan or coverage threshold. The root test script includes 15 packages; @biugle/biu-preset, @biugle/biu-adapter-react and @biugle/icons have no package test script. Preset owns the most complex layout, navigation, overlay, iframe and responsive behaviors. Manual verification of the Table page at three widths does not provide repeatable PR coverage.

Add browser smoke tests for Portal Sidebar/Topbar, React/Vue/HTML APP and Custom. Cover deep-link refresh, permission failure, iframe ready/error/retry, rejection of non-allowlisted Bridge messages, theme/locale/RTL, sidebar collapse, Drawer/Popover overlays and responsive Table behavior. Add keyboard focus, accessible-name, contrast and axe checks; include the browser suite in pnpm verify or a required CI job.

#### F-04 Production integration has no real-environment evidence (go-live blocker)

The project correctly assigns business SSO, permission decisions, gateway, CSP, domains, CDN, error monitoring and business menu APIs to the host platform, and documents them in docs/production-checklist.md. This run validated local services and mock Demos; it did not validate a production identity provider, real APIs, HTTPS security headers, frame-ancestors/frame-src, deployment SPA fallback, retention of old hashed assets, rollout or coordinated Portal/APP rollback. Having a configuration contract does not prove an integration has passed.

A production review needs a concrete environment matrix and acceptance record from the platform/business owners: authentication/login/logout/refresh and permission revocation, fail-closed menu behavior, exact Origins, CSP and Cookie attributes, redacted monitoring events, release rollback and deep-link refresh. Record an owner, environment, evidence and rollback procedure for each item.

The available evidence does not support a hash collision. Content hashes give different builds different URLs, but an old page can still request a lazy chunk removed by a deployment. ## 2026-10-26 Table Resizing, Code Security and Resource-Lifecycle Review

### Table column and row resizing

**The design passes; this review found no blocker that requires changing the public interaction model.** Column and row resizing are disabled by default and handles appear only when consumers opt in. Controlled values are committed through callbacks; uncontrolled values remain owned by Table. Resizing respects width/height bounds and supports fixed columns, grouped headers, RTL and virtual rows. Arrow keys and Home/End adjust dimensions, and handles expose separator semantics and the current value. Pointer up/cancel, window blur, layout configuration changes and component unmount end the active session and release global listeners and pointer capture.

For a non-virtual table, row-height preview updates only the active row and its cells; pointer movement no longer rerenders the entire table. Virtual rows still use React updates so the virtualizer can recalculate subsequent offsets. Column resizing snapshots the necessary columns and headers, then updates widths, compensation columns and the guide during pointer movement. Its work scales with column count rather than row count. This is a reasonable tradeoff for typical admin tables with tens of columns. If tables reach hundreds of columns or profiling shows dropped frames, compare animation-frame batching in a real browser before adding that complexity.

Two usability limits remain: the touch column handle is 18px wide and the row handle is 10px high. They are visible on coarse-pointer devices and use Pointer Events, but the row boundary is still difficult to hit precisely. Test a larger hit area on phones before shipping it, because it may cover actions in the last cell. A non-virtual Table still creates DOM for every data row; large data sets should use a stable rowKey and evaluate virtual rendering. Resize optimizations do not replace a data-size-appropriate rendering strategy.
